# RPM note — server-side PDF (design)

**Status:** DESIGN + BUILD. Replaces the browser-print path, which failed repeatedly, can't
produce a storable/sendable file, and created two ways to render a signed document that could
disagree. **One generator, server-side.** Billing/clinical artifact — the signed PDF must be a
faithful render of the hashed record. **Date:** 2026-09-14.

## Decisions (settled)
1. **Library: `@react-pdf/renderer`** — pure-JS, runs in Node, declarative layout with built-in
   page-wrap. NOT Puppeteer: Chromium is ~300MB + ~1GB+ RAM/render + cold start on a box already
   running Node + MySQL + nginx + the Vite dev server — a real OOM risk (§footprint) and its
   version can shift rendering, bad for a legal artifact. NOT PDFKit: imperative cursor-drawing is
   far more work for this dense, fixed template. Cost of @react-pdf: the layout is authored once in
   its primitives (the existing `rpmNote.css` is not reused). The template must stay faithful to the
   Quantix "Clinical Documentation Template" — do NOT redesign it.
2. **Endpoint:** `GET /api/patients/:patientId/rpm-note.pdf?month=YYYY-MM`. `authRequired` +
   `resolveOrgScope` + `scopePatientParam("patientId")` + the note-view role gate (org-wide roles +
   assigned clinician + **biller**, who needs it for claims). Signing stays clinician-only;
   *downloading* a signed PDF is a read, so it uses the broader view gate. Returns
   `application/pdf`, `Content-Disposition: attachment; filename="RPM-note_{mrn}_{month}.pdf"`.
3. **Signed → render the FROZEN snapshot; unsigned → live pre-fill, DRAFT.** `rpm_notes.content`
   is a frozen `{ computed, clinical, rules_fingerprint }` snapshot + `attestation_text` +
   `signature_name`/`signed_role`/`signed_at` + `content_hash` (SHA-256, anchored in `audit_log`).
   A signed PDF renders **entirely from that row** — never a live re-compute — so it matches the
   hash. No signed note → render the live pre-fill (`getRpmNote`, clinical blank) with the DRAFT
   treatment below.
4. **Signature block:** signed → the frozen attestation text, "Electronically signed by
   {signature_name}, {signed_role}, on {signed_at, clinic-tz}", an integrity line ("SHA-256
   {short} — verified against the record ledger"), note id/version, and a correction marker if it
   supersedes. Draft → blank signature lines under the DRAFT watermark.
5. **Storage — two phases:**
   - **Phase 1 (no S3 dependency): on-demand** from the frozen snapshot. Deterministically
     regenerable (see pinning), so on-demand is itself an authoritative artifact. Ships now.
   - **Phase 2 (Husnain's S3): generate once AT SIGNING, store the exact bytes** (keyed to note id +
     hash) in an SSE-KMS, BAA-covered, access-logged bucket — for immutable archival + sending.
     Store *at signing* so stored bytes == signed record. **PHI at rest → gated on his infra +ok.**
     Env-gated; inert until the bucket + credentials exist. Same renderer both phases.
6. **Footprint:** @react-pdf is pure JS, sub-second, tens of MB — fits t2/t3. Puppeteer would risk
   OOM on this shared instance; if a headless approach were ever needed it belongs on a separate
   worker, not this box.

## Emphasis 1 — the DRAFT watermark must be impossible to miss
An unsigned note WILL get downloaded, and it must be unmistakable that it is **not** the filed
document. Not a small footer tag — a **prominent, page-spanning diagonal "DRAFT — NOT SIGNED"
watermark on every page**, plus a header banner and blank signature lines. A draft and a signed
note must never be confusable at a glance or on a printout in a chart. Only a note rendered from a
signed `rpm_notes` row omits the watermark.

## Emphasis 2 — pin the renderer + lock fonts + lock metadata, and WHY (so it survives a year)
The signed PDF's integrity guarantee is that it can be **regenerated byte-for-byte** from the
hashed snapshot. That only holds if the rendering is deterministic. As built, THREE things secure
that; all three are load-bearing and all are recorded here because **nobody remembers it a year on**:

1. **Pin `@react-pdf/renderer` (and `react`) to an EXACT version** — `package.json` carries
   `"@react-pdf/renderer": "4.9.0"` and `"react": "19.3.0"`, no caret. A library upgrade can change
   layout/hyphenation/PDF structure → a regenerated PDF would differ from what was signed, breaking
   the "render matches the hash" property. **Do not bump either without re-validating against
   archived signed notes.** An innocent `npm update` is exactly the silent break this guards.

2. **Fonts: use the base-14 standard PDF fonts — do NOT ship `.ttf`.** The renderer uses
   **Times-Roman** (body) and **Helvetica** (headers/tables). `@react-pdf` bundles the AFM glyph
   metrics for the standard fonts *inside the library*, so layout is identical on any host/OS
   regardless of installed system fonts, with **no external font file to ship, version, or lose**.
   This is a deliberate refinement of the original "embed the .ttf" plan: it reaches the same goal
   (host-independent output) with fewer moving parts — determinism reduces to the single version pin
   in (1), because the metrics travel *with* that pinned version. (Trade-off: limited to
   Times/Helvetica/Courier, which is fine — the template only needs a serif body + a sans heading. A
   NOTE on drawn checkboxes: the base-14 fonts lack the ballot-box glyphs ☑/☐, so the template's
   checkboxes are drawn as bordered boxes with an "X", not typed characters.) If a branded/custom
   face is ever required, switch to `Font.register` with a **repo-committed** `.ttf` and re-validate
   byte-reproducibility at that point.

3. **Lock the PDF metadata.** PDFKit (under `@react-pdf`) stamps a live `CreationDate`/`ModDate` and
   derives the PDF file-ID from the Info dict, so at defaults **every render's bytes differ** — this
   alone defeats byte-for-byte regeneration and was found during build. The renderer therefore pins
   `creationDate`/`modificationDate` to the note's immutable signed instant and sets
   `producer`/`creator` to fixed strings (not the library-version default, so the version number is
   not baked into the bytes). With these fixed, two renders of the same signed row are byte-identical
   (verified in build). **Do not remove these overrides.**

Phase 2 (storing the exact bytes at signing) is the backstop — once stored, the archived bytes are
authoritative regardless of later renderer drift; on-demand regeneration is the fallback and needs
all three of the above.

## Build order
1. **Phase 1 — BUILT.** `services/rpmNotePdf.service.js` (`@react-pdf` template, faithful to
   `RpmNote.jsx`) + `renderRpmNotePdf({ note, clinical, signed })` returning a Buffer; controller
   `getRpmNotePdf` + route `GET /:patientId/rpm-note.pdf`; `getSignedContentForRender` accessor on
   `rpmNoteSign.service.js` for the full frozen snapshot. Both variants render-verified locally
   (draft: page-spanning watermark on every page; signed: attestation banner, frozen clinical
   fields, filled signature + SHA-256 integrity line), and the signed render is byte-identical across
   two runs. Still needs an **on-box** verify against a REAL signed row before the dashboard swap.
2. **Verify** the PDF looks right, then **swap the dashboard**: replace the "Save as PDF / Print"
   button with a "Download PDF" link to the endpoint, and **remove the print CSS + `window.print`
   path entirely** (the broken path goes away so nobody uses it). Ordered AFTER verification so a
   working PDF path always exists.
3. **Phase 2:** store-at-signing → S3 when Husnain's bucket is ready (env-gated; inert until then).

## Deployment prerequisites
- `npm install` on the box (adds `@react-pdf/renderer` + the embedded font files).
- Phase 2: the S3 bucket (SSE-KMS, BAA, access logging) + credentials/IAM before enabling.
